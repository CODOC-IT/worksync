DATABASE DESIGN SPECIFICATION Office Management System Normalized PostgreSQL Schema and Logical ERD A modular 3NF redesign derived from the functional specification and the roles, permissions, approval workflows, and notification specification. Design item Decision Database platform PostgreSQL 16+ (centralized database) Normalization target Third Normal Form (3NF) Physical scope 70 tables, 11 business schemas, reference data, indexes, and views Security model RBAC plus expiring project/department scopes Time standard UTC timestamps; local office dates remain business facts Baseline policy Create once; evolve with versioned migrations Prepared from supplied system documentation | 24 July 2026 1. Executive design summary The old TaskFlow database represented users, projects, tasks, and activity in four broad tables. That structure could support a small board, but it could not safely represent multiple assignees, temporary scoped responsibilities, peer review, attendance isolation, reusable files, discussions, leave, saved reports, notifications, or historical changes. The redesigned schema separates each independent business fact while keeping navigation and reporting efficient through indexes and views. Key outcomes 70 entities across 11 business schemas; each schema has one clear responsibility. Permanent roles and temporary Team Lead/HR responsibilities are modeled separately from project and department scope. No-self-approval is represented declaratively and reinforced by transactional authorization rules. Many-to-many facts—project members, task assignees, role permissions, attendees, mentions, and file links—use junction tables. Current values and historical facts are separated; assignments, statuses, permission changes, reviews, and audit events retain history. Dashboard cards, overdue flags, workload, and most calendar items are derived rather than stored redundantly. 2. Sources and interpretation The schema was derived from the supplied full functional documentation (v3.0) and the roles, permissions, approval workflows, and notifications specification. Where the documents use “Manager” and the later permissions document uses “Administrator,” the model avoids hard-coding either word into business tables. Both are RBAC roles; temporary Team Lead and HR duties remain scoped assignments. Normalization proof 5.1 First Normal Form Every table has a defined key and each column contains one value at the database level. Repeating groups from the functional requirements are separate relations: assignees, project members, milestones, dependencies, acceptance criteria, mentions, attendees, work-schedule days, correction items, and notification recipients. 5.2 Second Normal Form For tables with composite keys, non-key facts depend on the whole key. For example, RolePermissions contains only the RoleId-PermissionId relationship; EventAttendees stores the response for a specific EventId-UserId pair; and UserNotificationPreferences stores preference values for a specific UserId-NotificationTypeId pair. 5.3 Third Normal Form Descriptive values that depend on another non-key identifier have been moved to their owner. Project status names reside in ProjectStatuses, priority labels in Priorities, leave type properties in LeaveTypes, notification defaults in NotificationTypes, and report metadata in ReportDefinitions. Tasks retain only foreign keys to these classifications. Derived values such as overdue state, dashboard totals, and workload are views, not stored columns. Intentional structured payloads JSON is used only for variable-shape snapshots or typed proposed values: report filters, prompt context, and controlled field values. These payloads are not used as substitutes for core relationships. PostgreSQL JSONB provides native validation, indexing, and containment operators for these structured payloads. 6. Deployment guidance Deploy to PostgreSQL 16+ and manage all later changes through ordered, versioned migrations. Use one centralized PostgreSQL cluster with separate application schemas and a controlled connection pool. Store all timestamps in UTC and convert through the organization/user time-zone setting. Wrap approval decisions, target-row updates, audit insertion, and notification enqueueing in one transaction. Use least-privilege database users. The application account should not own the database. Use PostgreSQL Row-Level Security only after the exact tenancy and reporting access patterns are finalized. Use JSONB only for variable-shape snapshots; keep core relationships in normalized tables. Use partial indexes for active assignments, current members, unread notifications, and pending approvals. Treat audit and permission-history tables as append-only through database permissions. Create versioned migration and rollback scripts after the legacy data profile is inspected. Load-test dashboard, task board, activity, notification inbox, and attendance review queries against realistic volume.
